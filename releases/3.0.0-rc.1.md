# PlexonCrates 3.0.0-rc.1

PlexonCrates 3.0.0-rc.1 is the staging release candidate for the first Core-native 3.0 production line. It finalizes the existing `3.0-Update` architecture rather than replacing it.

## Highlights

- Optional PlexonCore 1.0 integration with `CORE`/`STANDALONE` operation, module ID `crates`, lifecycle health and diagnostics.
- Existing `PlexonCratesApi` and Bukkit event packages preserved; the PlexonQuests 3.1 `CrateOpenEvent` contract is locked by regression tests.
- PlexonKeys 1.2 stable Bukkit service API is the preferred live physical-key source, with the isolated compatibility adapter retained as fallback.
- Existing percentage-first 10,000-basis-point reward model, exact ItemStack snapshots, durable drafts, atomic publication, journal-first openings, Claim Inbox, milestones, rerolls, virtual keys and portable crates retained.
- Read-only PhoenixCratesLite migration framework with confined scanning, per-file SHA-256 hashes, deterministic source fingerprints and explicit fail-closed import while the live Phoenix schema remains unverified.
- Tag-driven release workflow with `SHA256SUMS.txt`, Java 25 verification, SQLite bundling checks and rejection of shaded PlexonCore/PlexonKeys runtime classes.

## Required staging gates

This release candidate is **not authorization for an immediate production Phoenix cutover**. Before final `v3.0.0`, validate on a cloned PlexonCraft server:

- `/plexon modules` shows PlexonCrates `READY`;
- `/quests diagnostics` shows `PLEXON_CRATES AVAILABLE`;
- PlexonKeys 1.2 live CONFIG/CAPTURED templates and exact fallback behavior pass;
- the operator-owned current PhoenixCratesLite data folder or sanitized exact fixture is supplied and a reviewed adapter is tested against it;
- every required Phoenix crate/key/reward/chance/location is represented and reviewed;
- controlled single/bulk openings, exact custom items, restart behavior and Phoenix-JAR-absent behavior pass;
- rollback data is prepared.

Until the actual Phoenix fixture is available, the migration framework intentionally reports `MANUAL_REVIEW` and keeps `IMPORT_TO_DRAFTS` blocked rather than guessing undocumented fields.
